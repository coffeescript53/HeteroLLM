01 The system

One model, two backends.
A boundary worth understanding.

The quantized model exceeds either GPU’s memory. llama.cpp can split its layers across NVIDIA and AMD, but understanding that execution requires reliable records of copies, waits, and graph submissions. HeteroLLM adds the tools to collect and check those records.

02 The repair

The run completed.
The first trace was unusable.

Repetitive event bookkeeping filled all 65,536 recording slots before useful copy records survived. A faster benchmark would not fix a measurement system that was losing the evidence.

  1. 01

    Identify what exhausted the recorder

    The initial diagnostic dropped 22,336 spans and retained no host-stage copies. The missing records made transfer count and cost unknown.

  2. 02

    Separate detail from repetition

    Aggregate event.record_submit and event.synchronize by backend and event kind. Preserve exact call counts and duration histograms, alongside individual routing, copy, and graph spans.

  3. 03

    Make incomplete evidence fail validation

    Reject loss, unfinished operations, overflow, invalid metadata, and inconsistent counters. A trace becomes usable only when its completeness checks pass.

instrumentation/v2/heterollm-cpu-trace.h

void aggregate_end(size_t slot, uint64_t elapsed) {
    if (slot == aggregate_capacity) return;
    std::lock_guard<std::mutex> lock(mutex_);
    if (slot >= groups_ || !aggregates_[slot].pending) { invalid_ = true; return; }
    Aggregate & a = aggregates_[slot]; --a.pending;
    add(a.count); add(a.total_ns, elapsed); add(a.histogram[histogram_bin(elapsed)]);
    if (elapsed > a.max_ns) a.max_ns = elapsed;
    add(aggregate_completed_);
}

Actual source excerpt. Completing an aggregate records the call count, total duration, maximum, and histogram bin under a mutex. Copy and graph records use a separate detailed-span path, so frequent event calls no longer consume that buffer.

Reliable execution is part of the experiment.

The Python supervisor checks runtime identity and resources, watches physical GPU sensors, records failures, and terminates the entire owned process group when a run must stop.

  • Memory, thermal, and wall-clock admission / stop conditions
  • Bounded sensor readers and stale-sample rejection
  • TERM → KILL cleanup with process-group verification
  • Durable result records, including failed attempts

What the project contributes

Instrumentation, supervision, validation, and analysis. llama.cpp supplies heterogeneous execution, model loading, quantized kernels, layer placement, and scheduling. These boundaries are documented in docs/CONTRIBUTIONS.md and NOTICE.md.

Where the research stands

The baseline and measurement work is complete within its stated scope. A later CUDA-heavier placement candidate failed its strict numerical gate; a subsequent quality attempt was incomplete. No controlled placement speedup or quality-preservation result is claimed.
